## The problem this solves

Three distinct user types share two routing shells today:

```
/(app)/   ← BOTH B2B planner-served couples AND B2C self-serve couples
/(admin)/ ← Planner admins (Astia)
```

The `/(app)/` shell renders **identical components** for:
- **B2B planner-served couples** (Hursh & Nisha, Sara & Marcus, Anaya & Rohan, Jennifer & Liam — all served by Astia)
- **B2C self-serve couples** (Kyle & Michelle, John, Rachel & Jay, rodnj.ops)

They have different needs, different data shapes, different feature expectations. The shell can't tell them apart. **Wave 3 worker agents (last session) shipped B2C dashboard features and instantly nuked the B2B planner-served portal because there was no architectural fork point.** Same disease produced 4 of the 12 May 8 regressions.

This T1.5 task introduces the fork point. After this lands, you can ship a B2C-only feature without touching B2B (and vice versa).

---

## Core abstraction: `WorkspaceMode`

A new type that captures which experience the workspace should render:

```ts
export type WorkspaceMode =
  | "b2c"                       // Self-serve couple. Skin: acquired_planner.
  | "b2c_acquired_style_collab" // Future Brigette co-brand. Skin: acquired_style_collab.
  | "b2b_co_branded"            // Planner-served couple. Skin: co_branded.
  | "b2b_white_label";          // Planner-served couple, premium tier. Skin: white_label.
```

Resolution rule:

```ts
function resolveWorkspaceMode(skin: WorkspaceSkin): WorkspaceMode {
  switch (skin) {
    case "acquired_planner": return "b2c";
    case "acquired_style_collab": return "b2c_acquired_style_collab";
    case "co_branded": return "b2b_co_branded";
    case "white_label": return "b2b_white_label";
  }
}
```

Convenience helpers for downstream:

```ts
export function isB2C(mode: WorkspaceMode): boolean
export function isB2B(mode: WorkspaceMode): boolean
export function isPlannerServed(mode: WorkspaceMode): boolean
```

Most pages will switch on `isB2C(mode)` or `isB2B(mode)` for clarity.

## Implementation flow

### Step 1 — `lib/workspace-mode.ts`

Pure module, no React. Exports the type, the resolver, the predicates. Importable from server + client.

```ts
import type { WorkspaceSkin } from "@/lib/workspace-skin";

export type WorkspaceMode =
  | "b2c"
  | "b2c_acquired_style_collab"
  | "b2b_co_branded"
  | "b2b_white_label";

export function resolveWorkspaceMode(skin: WorkspaceSkin): WorkspaceMode { ... }
export function isB2C(mode: WorkspaceMode): boolean { ... }
export function isB2B(mode: WorkspaceMode): boolean { ... }
export function isPlannerServed(mode: WorkspaceMode): boolean { ... }
```

### Step 2 — `components/workspace/workspace-mode-provider.tsx`

Client component. Wraps children with a context provider so any descendant client component can read mode via `useWorkspaceMode()`.

```tsx
"use client";
import { createContext, useContext } from "react";
import type { WorkspaceMode } from "@/lib/workspace-mode";

const WorkspaceModeContext = createContext<WorkspaceMode>("b2c");

export function WorkspaceModeProvider({
  mode,
  children,
}: { mode: WorkspaceMode; children: React.ReactNode }) {
  return (
    <WorkspaceModeContext.Provider value={mode}>
      {children}
    </WorkspaceModeContext.Provider>
  );
}

export function useWorkspaceMode(): WorkspaceMode {
  return useContext(WorkspaceModeContext);
}
```

### Step 3 — `(app)/layout.tsx`

Already loads `skin` via `normalizeSkin(workspaceSkin)`. Add:

```ts
const mode = resolveWorkspaceMode(skin);
```

Wrap `{children}` with `<WorkspaceModeProvider mode={mode}>`.

Server components in pages can also import `resolveWorkspaceMode` directly and re-derive mode from the workspace they fetch.

### Step 5 — Refactor pattern per divergent page

For each forking page, the pattern is:

```tsx
// server component
import { resolveWorkspaceMode, isB2B } from "@/lib/workspace-mode";

export default async function SomePage() {
  // ... existing data fetching ...
  const mode = resolveWorkspaceMode(skin);

  if (isB2B(mode)) {
    return <SomePageB2B data={...} />;
  }
  return <SomePageB2C data={...} />;
}
```

Existing big inline JSX gets extracted to `SomePageB2C` (default) and `SomePageB2B` (new variant). Both live in the same file initially — refactor to separate files only when a variant exceeds 200 lines.

## Decisions made

1. **Single file per page with two inline variants**, not separate files. Easier to keep in sync, easier to spot drift. Refactor to separate files when variants > 200 lines.

2. **No new routes.** `/planner-portal/*` was considered but rejected — same URLs simpler to share, easier to backlink, supports impersonation (planner viewing client's portal renders the client's mode).

3. **Mode resolved server-side in layout, provided via React context to client components.** Server components in nested routes call `resolveWorkspaceMode(skin)` directly with their own workspace fetch. Both paths converge on the same `WorkspaceMode` value.

4. **No mode override mechanism in v1.** A future "View as B2C" toggle for planners could come later but doesn't ship now — KISS.

5. **Existing forks in /estimator and /pricing stay as-is.** They use data-shape detection (`budget_estimates.length > 0` vs `budget_lines.length > 0`). We don't refactor those to use `mode` in this pass because they work correctly. They'll get harmonized in a future cleanup pass.

## Risk + mitigation

| Risk | Mitigation |
|---|---|
| Refactor introduces regression on either B2B or B2C | T1.4 smoke tests catch this. Ship T1.5 + T1.4 together. |
| Astia workspaces still on `acquired_planner` skin (per Hursh & Nisha rollback May 8) means B2B fork won't trigger on them | Need to either (a) backfill `workspace_branding` for Astia clients + flip them to co_branded, OR (b) ship T1.5 with the fork wired but skin still acquired_planner — both paths still render correctly because mode defaults to b2c. Path (b) is safer; do (a) as a separate task. |
| Race condition: workspace_id changes mid-session (e.g. planner impersonation) | The layout re-fetches mode on every request (server component). No client-side cache to invalidate. |
| Performance: extra query for skin | Already done in current layout. No additional cost. |
