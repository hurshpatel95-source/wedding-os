# T1.1 — Migration Auto-Apply

**Sprint item:** Stabilization Tier 1, item 1
**Status:** Shipped May 11, 2026
**Owner:** Hursh + Claude

---

## The problem this solves

Migrations live as SQL files in `supabase/migrations/` but only land
on the prod DB when Hursh manually pastes the SQL into the Supabase
dashboard SQL editor. This produced the May 8 `/plan` task cost-link
regression: the code referenced `planning_tasks.budget_line_id`, the
migration was committed, but the SQL was never pasted. Real user
clicked the feature → 500.

This T1.1 task eliminates that class of bug by automating migration
application on every Railway deploy.

---

## How it works

1. **Tracking table:** `_acquired_migrations` (filename, sha256, applied_at, applied_by)
   - Auto-created by the migrator on first run
   - Lives in the same DB as everything else
2. **Migrator script:** `supabase/seed/_migrate.ts`
   - Reads `supabase/migrations/*.sql` sorted alphabetically (timestamp prefix = chronological order)
   - Diffs against the tracking table → list of pending migrations
   - Applies each in a transaction, records the sha256 hash + filename + applied_by
   - Falls back to auto-commit DDL for migrations that can't run in a transaction (e.g. `ALTER TYPE ... ADD VALUE`)
   - Exits non-zero on any failure
3. **Railway hook:** `railway.json` has `"preDeployCommand": "pnpm migrate"`
   - Railway runs migrate AFTER build success but BEFORE container starts serving traffic
   - If migrate fails (non-zero exit) Railway aborts the deploy and rolls back
   - The old container keeps serving until a successful migrate

## Required env vars

Add to Railway service env (and locally if running outside CI):

| Var | Where to get it |
|---|---|
| `SUPABASE_DB_URL` | Supabase dashboard → Project Settings → Database → Connection string (use the direct connection, not pooler, for DDL) |

Format: `postgresql://postgres:[YOUR-PASSWORD]@db.dfyryyzizxcxtysduono.supabase.co:5432/postgres`

Without `SUPABASE_DB_URL` the migrator exits 1 with a clear error.

## Usage

```bash
# Apply pending migrations
SUPABASE_DB_URL=postgres://... pnpm migrate

# Just check what's pending without applying
SUPABASE_DB_URL=postgres://... pnpm migrate:status

# In Railway: runs automatically as preDeployCommand
```

## What about the migrations that have already been pasted manually?

The first time `pnpm migrate` runs against the prod DB, it'll see 34
SQL files and an empty tracking table → conclude all 34 are "pending"
and try to apply them. Some will fail because the schema already
exists (e.g. CREATE TABLE conflicts).

**Two mitigation paths:**

**(a) Mark all current migrations as already applied (preferred).** One
backfill operation: insert 34 rows into `_acquired_migrations` with
the existing filenames + their sha256 hashes. Future migrations get
auto-applied normally. Documented in this file as a one-time step.

**(b) Idempotent migrations only.** All migrations use `IF NOT EXISTS`
/ `IF NOT EXISTS` patterns so re-running is safe. Most of our existing
migrations already do this; a few don't. Path (a) is safer because it
avoids any risk of running a destructive migration twice.

**We're doing (a).** See `Backfill script` below.

## Backfill script

To run ONCE after this T1.1 ships, marking all current migrations
as applied without re-running them:

```bash
SUPABASE_DB_URL=postgres://... pnpm tsx supabase/seed/_migrate_backfill.ts
```

The backfill script inserts every existing migration filename into
`_acquired_migrations` with the current sha256 + `applied_by='backfill-2026-05-11'`.
After this runs once, `pnpm migrate:status` will show 0 pending,
and the next NEW migration committed will be the first one auto-applied.

## Failure modes

| Failure | Behavior |
|---|---|
| `SUPABASE_DB_URL` missing | Migrator exits 1, Railway preDeploy fails, deploy aborts |
| Migration SQL has syntax error | Transaction rolled back, migrator exits 1, deploy aborts |
| Schema conflict (e.g. table already exists, non-idempotent migration) | Migration fails, deploy aborts, you must fix the migration |
| Network blip mid-apply | Partial state: applied migrations are tracked. Next run picks up where this left off. |
| Multi-instance race condition | Tracking table has PRIMARY KEY on filename — second instance gets `ON CONFLICT DO NOTHING`. First instance wins. |

## Verification

After deploy:

1. SSH into Railway service (or check logs) — see `✓ Applied N migration(s) successfully.`
2. Connect to DB and query `select * from _acquired_migrations order by applied_at desc limit 5`
3. Try committing a new test migration — push and watch Railway logs apply it
4. Smoke tests (T1.4) verify the runtime feature still works
