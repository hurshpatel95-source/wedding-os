# T1.3 — Write-Guard Pattern

**Sprint item:** Stabilization Tier 1, item 3
**Status:** Phase 1 — helper + applied to 5 exemplar endpoints (May 11). Phase 2: roll out to remaining ~110 routes.
**Owner:** Hursh + Claude

---

## The problem this solves

On May 8 the `/settings/preferences` API endpoint did:

```ts
await supabase
  .from("workspaces")
  .update(patch)
  .eq("id", workspace_id);
```

The query succeeded with **0 rows affected** because RLS
(`workspaces_admin_write` policy) only permits `role='admin'`, and
couples have `role='couple'`. PostgREST returned 200 with empty
result. The API returned `{ ok: true, ...patch }`. The UI toasted
"Saved." The user reloaded → saw their wedding date reverted → lost
trust in the product.

Same class of bug:

1. `/api/onboarding/complete` venue insert silently swallowed the
   `notes` column missing error
2. `/api/planning-tasks/[id]` PATCH would have silent-failed if RLS
   blocked the planning_tasks update
3. Probably 10+ other endpoints we haven't hit yet

**There are 115 mutation routes in apps/web/app/api/. Until this
sprint, none of them guarded against 0-row updates.**

---

## The fix

`apps/web/lib/db-write-guard.ts` exposes three helpers — `dbUpdate`,
`dbInsert`, `dbDelete` — that wrap a Supabase mutation, assert (a)
no DB error and (b) at least one row affected/returned, and throw
`DbWriteError` if either fails.

API endpoints catch `DbWriteError` and convert to a real HTTP error
(usually 500 with the description, or 403 if the failure looks
RLS-shaped). **No more silent successes.**

### Helper signatures

```ts
async function dbUpdate<T>(
  description: string,
  query: PromiseLike<{ data: T[] | null; error: ... }>,
): Promise<T[]>  // guaranteed non-empty

async function dbInsert<T>(
  description: string,
  query: PromiseLike<{ data: T[] | null; error: ... }>,
): Promise<T[]>  // guaranteed non-empty

async function dbDelete<T>(...): Promise<T[]>  // same shape

class DbWriteError extends Error {
  description: string;
  reason: string;
  details?: unknown;
}

function dbWriteErrorResponse(err: unknown): { status, body }
```

### Usage pattern

```ts
// BEFORE
const { error } = await supabase
  .from("workspaces")
  .update(patch)
  .eq("id", wsId);
if (error) {
  return NextResponse.json({ error: error.message }, { status: 500 });
}
return NextResponse.json({ ok: true });  // ← LIES if RLS blocked

// AFTER
try {
  await dbUpdate(
    "update workspace preferences",
    supabase.from("workspaces").update(patch).eq("id", wsId).select("id"),
  );
  return NextResponse.json({ ok: true });
} catch (err) {
  const { status, body } = dbWriteErrorResponse(err);
  return NextResponse.json(body, { status });
}
```

## Phase 1 — Helper + 5 exemplar endpoints (this commit)

Applied to the 5 highest-impact mutation endpoints. These are routes
that mutate user-visible state and would produce the worst experience
if they silent-failed:

| Endpoint | Why it's exemplar |
|---|---|
| `POST /api/workspace/preferences` | Already has the May 8 fix; refactor to use the helper as the canonical pattern. |
| `PATCH /api/planning-tasks/[id]` | Just shipped (cost-link feature); high-frequency UI usage. |
| `POST /api/budget-lines` | Couple's primary mutation point. |
| `PATCH /api/budget-lines/[id]` | Slider drag debounced PATCH. Lots of writes per session. |
| `PATCH /api/vendors/[vendorId]` | Vendor status pipeline + couple-facing edits. |

After Phase 1: ~10 of 115 endpoints use the guard. Pattern is
exemplified.

## Phase 2 — Roll out to remaining endpoints (DEFERRED)

**Scope:** Apply the helper to the remaining ~105 mutation routes.

**Estimated effort:** 1 day of mechanical refactoring.

**Why deferred:** Same reasoning as T1.2 phase 2. The pattern is
established; rollout is mechanical. Better to do in one focused
block than spread across the sprint. T1.4 smoke tests catch any
regression from the rollout.

**Phase 2 plan when picked up:**

1. Iterate over `apps/web/app/api/**/route.ts` files alphabetically
2. For each `supabase.from(...).update(...)` or `.insert(...)` or
   `.delete(...)`, wrap with the appropriate helper
3. Add `.select("id")` if missing (write-guard needs returned rows
   to count)
4. Wrap the call in `try/catch` + use `dbWriteErrorResponse`
5. Smoke test the endpoint manually
6. Commit per logical group of endpoints
